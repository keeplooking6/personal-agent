# 增量更新策略与面试问答

## 当前方案

### 执行顺序

1. `c2_summarize.py` — 拉取笔记，LLM 打标（note_type/insight_type/summary/tags）
2. `c3_chunk.py` — 切块，写入 `data/chunks.json`
3. `c4_incremental.py` — 增量同步（检测 `last_edited_time` 变化 → 全量重拉 → 重打标 → 重切块 → upsert Chroma）

### 核心特点：整篇笔记级别的全量更新

- 检测到 `last_edited_time` 变化 → 整篇重新拉取 markdown
- 删除该笔记在 Chroma 里的**所有旧块**（`collection.delete(where={"note_id": pid})`）
- 对全文**重新切块** → 全部重新插入
- enrichment 也重新调用模型打标

## 各步骤耗时分析

| 步骤 | 耗时预期 |
|------|----------|
| MCP 拉取一页 markdown（网络 → Notion API） | ~0.5–2s |
| `summarize_note()` 调本地 Qwen 打标 | ~1–3s |
| 切块（纯本地字符串操作） | <0.01s |
| Chroma 删除旧块 + 插入新块 | <0.1s |

在几十篇笔记、每次变动 1–3 篇的规模下，全量更新没有性能问题。

## 大规模场景的优化方向

如果规模到达几千篇笔记、每次几百篇变动、每篇几万字：

### 1. 基于 diff 的增量切块

不是按整篇笔记重切，而是：
- 存每个 chunk 的**文本哈希**（或 block_id 范围）
- 检测到变化后，用 diff 算法（Myers diff）找出真正变动的文本范围
- 只重建覆盖该范围及变长影响的 chunk

难点：chunk 边界会因文本插入/删除而漂移，需要漂移补偿机制。实践中常用更大的自然边界（如 Markdown 二级标题）作为 chunk 边界。

### 2. 异步/流水线架构

```
检测变化（扫描 last_edited_time）
  ↓
分发任务到队列（RabbitMQ / Redis Streams / SQS）
  ├── Worker 1: 拉取内容
  ├── Worker 2: Enrichment（可并行调用模型）
  ├── Worker 3: 切块
  └── Worker 4: 向量化 + 入库
```

每步独立 worker，消息队列解耦。这体现了**系统设计思维**而非单纯算法技巧。

### 3. 向量库增量写入

- Chroma 原生支持 `add()` 和 `delete()`，不需要重建 collection
- Pinecone / Qdrant / Weaviate 等生产级向量库都支持 upsert，不存在全量重建
- 当前 `d2_store_chroma.py` 的 `delete_collection + create_collection` 才是真正的性能问题

### 4. 打标成本控制

不是所有改动都值得重新调模型打标：
- 设**文本变化率阈值**（如改动超过 30% 才重新打标，否则沿用旧标签）
- 用 token 成本换一致性

## 面试问答要点

- 先承认**大部分场景不需要优化**：给出规模数字，说明全量更简单可靠
- 若追问大规模方案：从 diff 切块、流水线、向量库 upsert 三个方向回答
- **重点说 tradeoff**：全量和增量不是非黑即白，而是不同粒度上的选择
- 加分点：提到成本控制（变化率阈值），体现务实态度
- 面试官真正想听的：**你知道什么时候该用哪个方案，而不是背方案**

## 当前方案的合理边界

- 笔记量级：几十篇
- 每次变动：1–3 篇
- 每篇长度：几百到几千字
- 在此范围内，全量更新是最简单可靠的选择
- 超出此范围再考虑上述优化
