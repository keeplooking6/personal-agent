# 决策记录 #001：个人 Agent 从 RAG 演进到主动召回体系

**决策日期**：2026-07-13
**项目阶段**：Stage A-J 技术闯关已完成数据基础层（c1-c3, d1-d4, e1-e2）
**触发问题**：用户对"是否所有笔记都要拉本地做向量化"产生困惑，并意识到真实需求超出纯 RAG

---

## 一、当时面临的困惑（记录原始疑问）

1. **数据接入困惑**：目前是把 Notion 笔记拉到本地、切块、向量化存储。难道所有需要的笔记都要拉本地做这样的操作吗？我笔记有许多，目前只是练手拉几篇。
2. **架构方向困惑**：后续面向面试的正经项目，是否就需要通过模型实时总结笔记内容？
3. **核心需求困惑**：想让 AI 帮我分门别类整理"面对困境时的解决方案、支撑走过来的信念、聊天启发的灵感、金句、视频、自己的反思"，避免"收藏之后不再打开，收藏了就是会了"。
4. **演进路径困惑**：想按闯关方式一层层搭建 agent，并持续使用融入日常生活，而不是一次性项目。

---

## 二、关键认知演进（思考过程记录）

### 认知 1：混淆了"数据接入方式"和"是否向量化"

最初以为"拉本地 = 向量化 = RAG"，这三件事其实可以解耦：

- **数据接入方式**：全量本地 / 元数据索引+按需拉原文 / 纯 MCP 实时查询（三选一）
- **向量化粒度**：每个 chunk 一个向量 / 每篇笔记一个向量（摘要向量）
- **是否向量化**：可选，知识笔记适合向量化，部分结构化数据不一定需要

→ 这意味着不必二选一，可以分层组合。

### 认知 2："实时总结"不是银弹，总结有三个时机

| 时机 | 性质 | 用途 |
|---|---|---|
| 入库时总结 | 离线一次性 | 抽取摘要/标签/洞察，喂给 metadata |
| 查询时总结 | 在线按需 | 标准 RAG 的生成阶段 |
| 定期主题整理 | 离线批处理 | 主题聚类成结构化卡片 |

→ 最初以为"后续要实时总结"，实际最该补的是**入库时总结**和**定期主题整理**。

### 认知 3：RAG 解决"检索效率"，但解决不了"主动召回"

这是最关键的认知转折。用户的痛点"收藏了就是会了"本质是**不问就想不起来问**，这是召回问题不是检索问题。

- RAG 是被动式：你问 → 它答
- 用户的真实需求是主动式：你不问 → 它来找你

→ 光做 RAG 不够，需要在其上叠加结构化层 + 主动召回层。

### 认知 4：笔记类型分化，处理策略不能一刀切

用户笔记实际包含两大类，性质完全不同：

| 类型 | 例子 | 使用方式 | 适合的架构 |
|---|---|---|---|
| **知识笔记** | 技术学习、概念整理 | 问答式检索（"X 怎么用"） | L1 检索层足够 |
| **成长型笔记** | 困境方案、信念、灵感、金句、反思 | 主动召回、间隔复习、情境触发 | L1 + L2 + L3 全栈 |

→ 这两类不能混在一个 RAG 里处理，metadata 需要 `note_type` 字段区分。

## 三、最终架构决策：三层叠加体系

```
┌─────────────────────────────────────────────────┐
│ L3 主动层  │ 每日推送 / 间隔重复(SRS) / 情境触发 │  解决"收藏即学会"
│            │ 仅作用于成长型笔记                 │
├─────────────────────────────────────────────────┤
│ L2 结构层  │ 主题卡片库（困境卡/信念卡/灵感卡）  │  解决"分门别类"
│            │ 模型离线整理的结构化产物            │  仅成长型笔记进入
├─────────────────────────────────────────────────┤
│ L1 检索层  │ Chroma 向量检索 + metadata 过滤     │  解决"按需召回"
│            │ 知识笔记 + 成长型笔记全量进入       │  两类都进
└─────────────────────────────────────────────────┘
```

**关键设计**：
- L1 两类笔记都进，但通过 `note_type` metadata 区分检索行为
- L2/L3 只对成长型笔记生效，知识笔记不进卡片库（避免噪声）
- 知识笔记走标准 RAG 路径即可，不需要主动推送

## 四、数据接入策略决策

**当前阶段（练手 + 面试项目）**：保持全量本地 + 加 summarize 层

理由：
1. 笔记量级（几千篇内）本地完全扛得住，Chroma 几万条向量无压力
2. 离线可调试、可复现，面试演示稳定
3. 加 summarize 后存储增长可控

**切换信号（未来触发改造的条件）**：
- 笔记数 > 1 万
- 同步时间 > 10 分钟
- Chroma 内存吃紧

切换方式：改 `c1_pull_notes.py` 为"只拉 metadata"，原文走 Notion MCP 实时拉。局部修改，不推翻闯关成果。

## 五、闯关式演进路线（产品向 P1-P5）

与技术闯关 a-j 并行推进，每加一层对应一个真实使用场景：

### Stage P1：RAG 从"能用"升级到"好用"（本轮实施）
- 新增 `c2_summarize.py`：每篇笔记入库前生成 `summary + tags + note_type + insight_type`
- note_type ∈ {knowledge, growth}；insight_type ∈ {dilemma, belief, inspiration, quote, video, reflection}
- 字段塞进 Chroma metadata，检索时可按 type 过滤
- 评测集加分类召回题目

### Stage P2：结构化卡片层
- 新建 `cards/` 概念：每个 card = {type, content, source_note, created_at, related_cards}
- 写 `weekly_digest.py`：每周日扫本周新增成长型笔记，提取新卡片存到 SQLite
- 知识笔记不进入卡片库

### Stage P3：主动召回机制
- 接入 `j1_api.py`，做"每日推送"：每天早上选 3 张成长卡（SRS 间隔重复算法）推送
- 这是真正对抗"收藏即学会"的机制

### Stage P4：情境触发（长期）
- 写新笔记提到困境时，agent 主动检索历史相似困境，附上当时解决方案
- 依赖 agent loop（已有 `agent_core.py`）+ 写入 hook

### Stage P5：面试叙事化
- 把 P1-P4 演进做成简历可讲版本：从"练手 RAG demo"→"个人知识管理 agent"的完整演进
- 每一步对应一个工程决策，体现差异化思考

## 六、最终决策小结

| 决策点 | 结论 |
|---|---|
| 是否所有笔记拉本地 | 现阶段保持全量本地，未来按信号切换到元数据索引 |
| 是否实时总结 | 否，采用入库总结 + 定期主题整理的离线策略 |
| 纯 RAG 够不够 | 不够，需叠加 L2 卡片层 + L3 主动召回层 |
| 笔记类型处理 | 区分 knowledge / growth 两类，分别走不同架构路径 |
| 闯关方式 | 技术 a-j 与产品 P1-P5 并行，每层对应真实使用场景 |

## 七、P1 实施记录（本轮代码改造）

### 改造点 1：新增 `c2_summarize.py`
- 读取 `data/notes.json`
- 对每篇笔记调用 Qwen 模型，生成结构化字段
- 支持增量处理：已处理过的 note_id 跳过，避免重复调用
- 输出 `data/notes_enriched.json`

**Prompt 设计**：让模型输出 JSON：
```json
{
  "note_type": "knowledge | growth",
  "insight_type": "dilemma | belief | inspiration | quote | video | reflection | null",
  "summary": "一句话摘要",
  "tags": ["标签1", "标签2"]
}
```

**兜底策略**：
- 模型调用失败 → note_type 默认 knowledge，summary 取正文前 100 字
- 正文为空 → 仅基于标题做分类
- tags 为空时存空列表

### 改造点 2：修改 `pipeline.py`
- `build_chunks` 优先读 `notes_enriched.json`，无则回退到 `notes.json`（向后兼容）
- 每个 chunk 的 metadata 携带 `note_type`、`insight_type`、`summary`、`tags`
- `store_chroma` 同步把 enrichment 字段写入 Chroma metadata
- tags 以逗号分隔字符串存入（Chroma metadata 值不支持 list）

### 改造点 3：修改 `rag_core.py`
- `retrieve` 增加 `note_type_filter` 参数
- 通过 Chroma 的 `where` 条件实现按 note_type 过滤检索
- 不传 filter 时行为不变（向后兼容）

### 改造点 4：修改 `d3_retrieve.py`
- 支持 `--note-type knowledge|growth` 命令行参数
- 默认不过滤（检索全部笔记）

### 数据流

```
notes.json
   │
   ▼ c2_summarize.py
notes_enriched.json  (含 summary/tags/note_type/insight_type)
   │
   ▼ pipeline.build_chunks
chunks.json  (每个 chunk 携带 enrichment 元数据)
   │
   ▼ pipeline.store_chroma
Chroma  (metadata 含 note_type/insight_type/summary/tags)
   │
   ▼ rag_core.retrieve(note_type_filter=...)
按类型过滤的检索结果
```

## 九、复盘要点（供未来回看）

1. 当初最大的认知误区是把"RAG"等同于"个人 Agent"，忽略了 Agent 的主动性
2. "收藏即学会"的解法不是更好的检索，而是主动召回——这是个根本性的方向纠偏
3. 知识笔记和成长型笔记要分治，这是后续所有架构设计的前提
4. 闯关式搭建的关键不是"做完所有 stage"，而是"每加一层有真实使用场景"——否则会沦为 demo
