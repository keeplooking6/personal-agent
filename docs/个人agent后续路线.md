# Personal Agent 项目现状与后续行动参考

## 结论先行

“逐个运行脚本，跑通后再优化”的思路总体没问题，尤其适合当前这个教学型、模块化项目。

但不要机械地把所有脚本都跑一遍。应按“依赖顺序 + 是否会写外部数据 + 是否真的服务你的目标”来运行。真正的目标不是完成 A–J 打卡，而是逐步把已验证的能力收敛成一个能长期服务自己的产品。

当前项目已经具备个人 Agent 的重要基础：私有数据接入、RAG、长期记忆雏形、SQLite 会话、工具调用、规划、人工确认写入、观测、评估与 API。它尚未成为可持续运行的个人 Agent，主要缺少稳定运行机制、主动服务能力、安全与数据治理、以及统一的生产级状态管理。

## 一、项目当前状态

项目定位已经很清晰：

> 一个以 Notion 笔记为私有知识源、可进行 grounded 问答的 Personal Knowledge Agent；同时具备 MCP 实时工具调用、分层记忆、人工确认写入、评估与可观测性能力。

当前核心结构为：

```
flowchart TB
    U["用户 / API"] --> O["agent_core.py 路由编排"]
    O --> R["RAG：rag_core.py"]
    O --> T["MCP Tool Agent Loop"]
    O --> M["长期记忆：memory.json"]
    R --> V["Chroma 向量库"]
    V --> D["notes / chunks"]
    O --> X["TraceLogger"]
    E["eval_set + h2_eval"] --> R
```

已存在的数据基础：

- `data/notes.json`：已拉取的笔记。
- `data/chunks.json`：你已运行 `c3_chunk.py` 后生成的切块结果。
- `data/chroma/`：本地 Chroma 向量库目录已存在。
- `data/memory.json`：长期记忆文件已存在。
- `data/notes_enriched.json`：当前尚未生成。
- `data/chat.db`：当前尚未生成。
- `docs/reports/`：当前没有评估报告。

项目里还有一条非常正确的产品方向：把笔记区分为“知识笔记”和“成长型笔记”。知识笔记适合 RAG 问答；成长型笔记还应进入卡片、复习和主动召回系统。这个方向比单纯做一个“能查 Notion 的聊天机器人”更有长期价值。

## 二、你接下来不应该怎样跑

不要简单按文件名字母顺序或目录顺序全部执行。

原因：

- 有些脚本是前置能力演示，不是产品运行必需。
- 有些脚本会覆盖本地向量库，例如 `d2_store_chroma.py` 和 `run_experiments.py`。
- 有些脚本会调用模型，产生时间和算力成本，例如 `c2_summarize.py`、`h2_eval.py`。
- `g2_workflow.py` 在你输入 `y` 后可能向 Notion 写数据，属于外部副作用操作。
- 多 Agent、Plan-and-Execute 不是长期个人 Agent 的必需能力，应最后验证，不应优先投入。

## 三、建议的运行顺序

你已经运行到 `c3_chunk.py`。建议从这里开始这样走。

### 1. 先完成数据管道增强

优先运行：

```
python c4_incremental.py
python c2_summarize.py
python c3_chunk.py
python d2_store_chroma.py
```

说明：

- `c4_incremental.py`：验证增量同步思路，不必每次都执行。
- `c2_summarize.py`：这是当前最值得运行的一步。它会给笔记增加：
  - `note_type`：知识 / 成长
  - `insight_type`：困境、信念、灵感、金句、视频、反思等
  - `summary`：摘要
  - `tags`：标签
- 运行完 `c4` 后，必须重新运行 `c2` 和 `d2`，因为 `pipeline.py` 会优先使用 enriched 笔记来重建 chunks 与 Chroma metadata。
- `d2_store_chroma.py` 会重建 `notes` 集合；这是正常行为，但意味着它不是纯只读操作。

这一步的验收标准：

```
python d3_retrieve.py "什么是 RAG"
python d3_retrieve.py "如何面对焦虑" --note-type growth
```

你应能看到检索结果及其笔记类型；否则先不要进入后续阶段。

### 2. 再验证 RAG 是否真有用

```
python d4_rag_answer.py "我最近在学什么、有哪些项目？"
python h2_eval.py --top-k 3 --report docs/reports/baseline.json
python run_experiments.py
```

这里最重要的不是分数高低，而是建立“改动前后用同一评估集比较”的习惯。

验收标准：

- `baseline.json` 已生成。
- 你知道哪个问题答得差。
- 你能根据结果调整 `chunk_size`、`overlap`、`top_k`，而不是凭感觉改参数。
- 最后选定一组默认参数，并记录原因。

注意：`run_experiments.py` 会多次重建 Chroma；结束后向量库会停留在最后一组实验参数，而非最佳参数。选定最佳参数后，应手动再运行一次对应参数的 `c3_chunk.py` 与 `d2_store_chroma.py`。

### 3. 再做记忆与会话持久化

```
python e1_summary.py
python e2_memory.py
python f1_sqlite.py
```

这里要重点理解一个现状：

- `memory.json` 保存的是“关于你的长期事实”。
- `chat.db` 保存的是某个会话的消息历史。
- 目前 `f1_sqlite.py` 的 SQLite 会话能力与 `agent_core.py` 的 API 路径尚未统一接通。

因此，当前项目是“记忆能力分别演示成功”，而不是“API Agent 已完整具备跨会话上下文”。后续产品化时，这是需要优先整合的部分。

### 4. 最后再验证复杂能力

建议顺序：

```
python h1_observe.py
python g1_plan_execute.py "为我的个人知识管理 Agent 制定下一步改进计划"
python i1_multi_agent.py
uvicorn j1_api:app --reload --port 8010
```

关于 `g2_workflow.py`：

```
python g2_workflow.py
```

它涉及 Notion 写入。第一次只观察预览，除非你确认工具名称、参数与目标位置正确，否则不要输入 `y`。

## 四、哪些能力是“演示”，哪些是产品核心

| 能力                  | 当前价值           | 是否优先产品化 |
| --------------------- | ------------------ | -------------- |
| Notion 同步与增量同步 | 私有数据基础       | 高             |
| RAG 检索与出处回答    | 核心读能力         | 高             |
| 笔记分类、摘要、标签  | 个人知识管理核心   | 高             |
| SQLite 会话           | 持久化基础         | 高             |
| 长期记忆              | 个性化基础         | 高             |
| 评估与 Trace          | 持续改进基础       | 高             |
| MCP 工具调用          | 实时查询与行动能力 | 中高           |
| HITL 人工确认写入     | 安全写入基础       | 高             |
| Plan-and-Execute      | 复杂开放任务能力   | 中             |
| Multi-Agent           | 适合明确分工任务   | 低，后置       |
| FastAPI               | 对接界面与服务化   | 中高           |

一个重要原则：

> 能用确定性工作流完成的事，不要交给 Agent 自由发挥；能用单 Agent 完成的事，不要急着拆多 Agent。

## 五、可持续运行的个人 Agent 还需要什么

“私有数据、长期记忆、长驻运行”是必要条件，但还不够。一个真正持续有用的个人 Agent，至少还需要以下六类能力。

### 1. 明确的长期目标与服务场景

Agent 不能只是“什么都能聊”。它必须有明确的长期职责，例如：

- 帮我回顾并调用个人笔记。
- 将成长型笔记整理成困境卡、信念卡、灵感卡。
- 每日或每周提醒我回顾重要内容。
- 在我遇到类似困境时，召回我以前的解决方案。
- 协助把零散记录变成可行动的计划。

建议把项目的第一产品目标定为：

> 让个人笔记从“存档”变成“可检索、可整理、可主动回顾、可辅助行动”的系统。

### 2. 数据治理与同步可靠性

需要逐步补齐：

- 同步状态：每篇笔记的来源、更新时间、同步时间、版本。
- 删除策略：Notion 中删除或归档后，本地如何处理。
- 失败重试：模型、MCP、网络失败后如何重试。
- 数据备份：`notes.json`、`memory.json`、SQLite、卡片数据的备份策略。
- 可追溯性：每个摘要、标签、卡片能追溯到原始笔记。

当前的 `c4_incremental.py` 是这个方向的起点，但后续应把同步变成可重复、可恢复、可审计的任务。

### 3. 主动服务，而不只是被动问答

RAG 的模式是“你问，它答”；个人 Agent 更有价值的模式是“你没问，它仍在合适的时候帮到你”。

建议优先实现：

- 每周回顾：整理本周新增笔记、待完成事项、成长洞察。
- 每日召回：从成长型卡片中推送少量值得复习的内容。
- 间隔重复：根据上次回顾时间安排复习。
- 情境触发：当你写下“焦虑、拖延、项目延期”等内容时，推荐历史相似困境及你的解决方案。

这正是项目设计文档中 L2 卡片层和 L3 主动召回层的价值所在。

### 4. 安全边界与用户控制

个人 Agent 一旦能写入、发送、删除或调用外部工具，安全比“聪明”更重要。

应具备：

- 读与写权限分离。
- 所有外部写入默认预览、明确确认。
- 写入日志：写了什么、写到哪里、何时写的。
- 可撤销或至少可定位修改。
- 工具白名单与参数校验。
- 敏感信息最小化存储。
- API 鉴权；当前 FastAPI 的 CORS 为全开放，适合本地开发，不适合公网暴露。

### 5. 统一的状态与记忆架构

当前记忆有多个位置：

```
当前消息列表 → 临时上下文
SQLite → 会话历史
摘要 → 长会话压缩
memory.json → 用户长期事实
Chroma → 外部笔记知识
```

方向是对的，但后续应统一：

- `agent_core.py` 调用时加载对应 `conversation_id` 的 SQLite 历史。
- 达到阈值后自动摘要，而不是只在演示脚本中摘要。
- 长期事实应有来源、置信度、更新时间与可编辑能力。
- 用户可查看、修改、删除 Agent 记住的内容。
- 记忆写入应避免把模型猜测当成事实。

### 6. 可靠运行与成本控制

“长驻运行”并不是启动 `uvicorn` 后不关，而是可恢复地运行。

未来需要：

- 定时器或任务调度器：例如每日同步、每周整理、定时回顾。
- 任务队列：耗时总结、批量 embedding 不应阻塞聊天请求。
- 健康检查、日志、错误告警。
- 模型调用超时、重试、降级。
- Token / 模型调用成本记录。
- 进程重启后仍可恢复任务状态。
- 本地部署方式：先用简单的 Windows 任务计划程序即可，后续再考虑 Docker 或服务管理。

## 六、推荐的产品演进路线

### P1：先把“能查”做成“查得准”

目标：稳定的个人笔记 RAG。

- 完成 `c2_summarize.py`。
- 按 `knowledge / growth` 分类检索。
- 跑基线评估与参数实验。
- 为每次回答保留出处。
- 增加“不知道就拒答”的测试。

完成标准：

> 对 20 条评估题有可复现报告；能解释默认 chunk、overlap、top_k 的选择。

### P2：做成长型笔记卡片层

目标：让洞察不再只是原始笔记。

建议的卡片结构：

```
{
  "id": "card_xxx",
  "type": "dilemma",
  "content": "遇到项目延期时，通过拆解任务和同步风险降低焦虑。",
  "source_note_id": "notion_page_id",
  "created_at": "2026-07-17",
  "last_reviewed_at": null,
  "next_review_at": null
}
```

先实现：

- 困境卡
- 信念卡
- 灵感卡
- 每周新增卡片整理

### P3：做主动召回

目标：解决“收藏即学会”。

先不要急着接消息推送平台，可以先做：

```
python weekly_digest.py
python daily_recall.py
```

输出到终端或本地 Markdown 即可。验证有价值后，再接入通知渠道。

### P4：统一 AgentCore、会话与记忆

目标：API 调用也能拥有真实的连续会话。

需要：

- `conversation_id`
- SQLite 历史加载
- 自动摘要
- 长期事实的可控写入
- 用户可查看和清除记忆

### P5：服务化与日常使用

目标：不是 Demo，而是每天能用。

- API 身份校验。
- 本地定时运行同步与回顾。
- 任务日志与错误记录。
- Web UI 或现有 Next.js 界面对接。
- 每周复盘：它是否真的帮助你想起、理解或行动？

## 七、当前最优先的下一步

你现在最应该做的不是立即跑完所有脚本，而是完成这一段闭环：

```
c4 分类摘要
→ c2 重新切块
→ d2 重建向量库
→ d3 验证分类检索
→ d4 真实问答
→ h2 基线评估
→ run_experiments 参数对比
```

这是从“教程 RAG”进入“个人知识管理 Agent”的关键转折点。

完成后，再把注意力转向：

```
成长型笔记卡片
→ 每周整理
→ 主动回顾
→ 定时运行
```

## 八、判断一个功能是否值得加入的标准

每加一个功能前，问自己四个问题：

1. 它解决了我真实日常中的什么问题？
2. 它能否通过一个可复现的指标或实际体验验证？
3. 它是否比现有方式更省时间或更容易坚持？
4. 它会不会引入不必要的复杂度、成本或失控风险？

如果一个功能只是“看起来像 Agent”，但无法改善你的真实使用体验，就先不做。

## 最终方向

这个项目最有价值的终点，不是一个会调用很多工具的通用 Agent，而是：

> 一个由你掌控私有数据、能够理解你的知识与成长记录、会在恰当时机帮你回忆、整理与行动，并且安全、可追溯、长期可靠运行的个人认知系统。
